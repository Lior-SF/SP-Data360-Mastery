# Salesforce Personalization vs Marketing Cloud Personalization

## Scope

- Two separate products. **SP** = Salesforce Personalization, the Data 360–native Customer 360 app sold with Marketing Cloud Next. **MCP** = Marketing Cloud Personalization, the standalone real-time personalization platform formerly Interaction Studio and Evergage.
- Use this file to tell the products apart, avoid transferring MCP concepts to SP, and plan coexistence or migration ("Marketing Cloud Next for Personalization").
- Every MCP statement is tagged **MCP** and cites MCP sources (`developer/personalization`; Help `mc_pers_*`, breadcrumb `Salesforce Help|Docs|Marketing Cloud Personalization`). The `mc_pers_mcn_for_pers_*` migration pages sit under the MCP breadcrumb but describe both products. Release 264.0.0 unless noted.
- Tags: (UNVERIFIED) = not confirmed in docs during the latest verification pass.

### Triage procedure for ambiguous inputs (guidance derived from the tables above)
1. Source first: dev-doc path or Help breadcrumb; `mc_pers_mcn_for_pers_*` pages describe the MCP → SP bridge.
2. Code tokens next: `Evergage`, `mcis`, `getCampaignResponses`, `/authevent`, `ConsentPurpose.Personalization` → **MCP**; `Personalization.fetch`, `personalization: { dataspace }`, `/personalization/decisions`, `fetchDecisions`, `ConsentPurpose.Tracking` → SP.
3. Nouns: Einstein Recipe, Gear, dataset, identity type, Visual Editor, Event API, triggered/Open Time Email campaign → **MCP** only; personalization point, content schema, recommender, WPM, data space, data graph, batch personalization → SP only.
4. Overloaded words — campaign, experience, template, decision, content zone, "Personalization module" — resolve by context (§4) before answering.
5. Both products present (e.g. `Evergage` plus Data 360 DMOs) → coexistence or migration (§5).

## Gaps and uncertainties
- "Formerly Einstein Personalization" is stated only in a Salesforce Developers Blog post; no Help, dev-guide or release-note page (releases 260–264 indexed) states the rename. Heritage survives in URL/file slugs.
- The exact sentence "If no consent configuration is provided, all users are treated as opted-out" appears only on an MCP-breadcrumb migration page. SP-authoritative sources (Data 360 Interactions SDK Consent page) state the equivalent behavior in different words: no data is stored or transmitted until explicit `Opt In`.
- Coexistence changes "the namespace on the Data 360 side" but the new namespace name is not documented. The requirements page says the products "can't coexist without" MC Personalization+, then offers the SP-side coexistence toggle as an alternative.
- Cookie security conflict: the **MCP** web-integration guide says MCP cookies default to `secure` (dataset override `Web SDK Cookie Secure Attribute`); the migration article says the MCP SDK sets `secure: true` only when configured. The cookie-differences article also says SP uses "only `_sfic_*`" (typo for `_sfid_*`) and calls `_sfid_` the MCP "Primary identity cookie", while the MCP guide says `_sfid_` stores consents.
- Quicklook maps `Evergage.addResponseListener()` → `Evergage.CustomEvents.OnEventResponse` (still `Evergage`) — unclear for a Data 360 sitemap.
- WPM permission naming: "Web Personalization Manager user permission set" (access article) vs `Personalization Admin` / `Personalization User` permission sets (prerequisites article).
- Targeting option labels differ between "Add a Decision" (`… Rules …`) and "Create a Targeting Rule" (`… Conditions …`).
- Not researched: MCP mobile SDK method names, MCP campaign-statistics metric definitions, MCP segment membership triggers, MCP Agentforce integrations (none found).
- No SP equivalents documented for **MCP** triggered campaigns, Open Time Email, surveys, third-party campaigns.
- "MC Personalization+" edition vs `MCP+` SKUs in billing docs: likely the same offer (UNVERIFIED).

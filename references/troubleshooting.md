# Troubleshooting Playbook

## Scope
- Diagnoses web delivery and measurement failures in Salesforce Personalization (SP): the Salesforce Interactions SDK (Web SDK) with the Personalization module, the Data 360 sitemap, consent and identity, Web Personalization Manager (WPM), experience templates, the Decisioning API, engagement tracking, attribution, and Data 360 queries.
- Not for Marketing Cloud Personalization (MCP, formerly Interaction Studio / Evergage). Advice that mentions `Evergage`, `getCampaignResponses`, campaign statistics, implicit consent, or `mc_pers_*` / `developer/personalization` pages is MCP and doesn't apply here.
- Documented facts carry `[src](url)`. "(Field-observed, undocumented)" marks behavior seen in live SP implementations but absent from the docs; re-test it after SDK upgrades and seasonal releases. "(UNVERIFIED)" marks useful claims no doc confirms.
- Placeholders: `<POINT_ID>`, `<POINT_API_NAME>`, `<PAGE_TYPE>`, `<TENANT_ENDPOINT>`, `<PARENT_DOMAIN>`, `<CMP_NAME>`, `<TARGET_SELECTOR>` (target element, for example `#<TARGET_ID>`), `<TEMPLATE_API_NAME>` (experience template). Examples use a single rendered slot; the same checks apply to overlays, recommendation strips and handler-rendered zones. `Q1`–`Q10` refer to `sql-cookbook.md`.

## Triage order
Walk the pipeline in order and stop at the first failing stage. SDK logging is off by default (`none`, value 0), so start every session with this console snippet [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-debugging.html) [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-integration.html) [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html):

```js
SalesforceInteractions.setLoggingLevel('debug');
const CE = SalesforceInteractions.CustomEvents;            // bind via the constants (values are 'interactions:*')
document.addEventListener(CE.OnPageMatchStatusUpdated, (e) => console.table(e.detail.matchStatus));
document.addEventListener(CE.OnEventSend, (e) => console.log('sent', e.detail.actionEvent));
document.addEventListener(CE.OnException, (e) => console.error(e.detail.context, e.detail.error));
// Then reload the page (DevTools "Preserve log") rather than calling reinit(): reinit re-sends the page interaction
// and a decision request (Field-observed, undocumented).
```
- The integration page lists the constants as `interactions:onEventSend` etc., but its listener example uses `"salesforce:onEventSend"` (doc conflict) [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-integration.html). Binding via `CustomEvents` avoids the question.
- After `reinit()` the page interaction is sent again (Field-observed, undocumented; the docs only say it re-runs sitemap evaluation [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html)).
- To collect wire payloads and a device-ID / identity / consent probe at each UAT step, see [field-guide-web.md](field-guide-web.md) §7.

1. **Sitemap build loaded.** DevTools → Network: the connector's CDN script returns 200 (the SDK and the uploaded sitemap are hosted together on the CDN) [src](https://developer.salesforce.com/docs/data/data-cloud-int/guide/c360-a-salesforce-web-sdk.html). Console: `typeof SalesforceInteractions.reinit === 'function'`, and the snippet prints a `matchStatus` table. If the logic looks stale, confirm the latest file went up through **Upload | Replace Sitemap** on the website connector [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_qs_configure_website_connector.htm&release=264.0.0&type=5). During UAT, a `console.info("[SITEMAP] v<N> <date>")` banner on the sitemap's first line shows a stale upload or cached copy at a glance; remove it before go-live (Field-observed; [field-guide-web.md](field-guide-web.md) §3.3). The Sitemap Builder `Debug` mode shows the Data 360 event structure and personalization decisioning payloads [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_qs_sitemap_bldr_modes.htm&release=264.0.0&type=5).
2. **Consent opted in.** `SalesforceInteractions.getConsents()` returns an entry whose `consent.purpose` is `Tracking` and `consent.status` is `Opt In`; the SDK stores and sends nothing before that [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-consent.html) [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-consent-data.html).
3. **Page type matched.** Exactly one `matchStatus` row is `selected`, and it's the page type you expect; evaluation stops at the first match [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-integration.html). Events carry that name as `sourcePageType` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-translating-sdk-events-to-web-connector-schemas.html).
4. **Experience matched.** The debug line "matched enabled personalization experience config names" lists the WPM experience (Field-observed, undocumented). If it's missing, check the experience's State, its Location (`Current Page Type` or `Page URL`), and the data space.
5. **Decision fetched.** Network: `POST https://<TENANT_ENDPOINT>/personalization/decisions` returns your point in `personalizations[]` with `attributes` (Dynamic Content) or `data` (Recommendations) populated [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-request-personalization.html). Unauthenticated calls return no diagnostics; their codes go to the Personalization Log entry [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html). Manual probe: `SalesforceInteractions.Personalization.fetch(['<POINT_API_NAME>']).then(console.log)` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/request-personalization-through-sitemap.html); it's a real request, logged like production traffic (inference).
6. **Render target found.** `document.querySelectorAll('<TARGET_SELECTOR>').length === 1`. The debug line "flicker defense currently hiding the following transformations" lists each `{transformerName, tag, path}`, then "handling personalization response" appears (Field-observed, undocumented). A returned decision proves nothing about rendering: the dependable check is a `[data-sf-personalization-id]` element inside the target, and an empty "hiding … []" line isn't a reliable sign of a missing anchor (Field-observed, undocumented).
7. **View/click events sent.** In the Network payload to Data 360, look for `eventType` `userEngagement` with `interactionName` `personalization-view` (later `personalization-click`), carrying `personalizationId` and `personalizationContentId`; experiences using the Product Engagement destination (recommendations) send `catalog` events named `catalog-object-view-start` / `catalog-object-click` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/track-personalization-engagement.html). The debug line "Observing element for visibility" means view tracking is armed (Field-observed, undocumented).
8. **Data landed in DMOs.** Q1 returns views and clicks for `<POINT_ID>`. Website connectors ingest by streaming [src](https://help.salesforce.com/s/articleView?id=data.c360_a_data_stream_schedule.htm&release=264.0.0&type=5), but no end-to-end latency is documented for them, so send a known test event and wait for it before concluding data is missing.

## Symptoms: SDK load and page lifecycle

### Symptom: Flicker defense, engagement destinations, or experience configs are ignored
- **Cause:** `SalesforceInteractions.Personalization.Config.initialize(...)` ran after `SalesforceInteractions.init(...)`. Module initialization must happen before the sitemap initializes [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/initialize-einstein-personalization-module.html).
- **Confirm:** Read the call order in the sitemap source. With debug logging on, the "Set Flicker Defense Config to the following" line (Field-observed, undocumented) appears late or never.
- **Fix:** Call `Config.initialize` first at the top of the sitemap, then `init()`, then `initSitemap()` inside `init().then(...)` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/initialize-einstein-personalization-module.html) [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html).

### Symptom: Single-page app (SPA) route changes show stale, missing, or duplicated personalization
- **Cause:** SPAs must call `reinit()` on virtual navigation so the sitemap is re-evaluated [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html). Calling it before the new route's DOM exists targets missing elements; calling it several times per navigation fires duplicate fetches and impressions (Field-observed, undocumented).
- **Confirm:** Per route change, count `OnInit` events (the documented SPA debugging hook [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-integration.html)) and `/personalization/decisions` requests in Network. More than one per navigation is a reinit storm.
- **Fix:** Documented baseline: inside `init().then()`, poll `window.location.href` and call `reinit()` on change; the SDK example polls every 200 ms [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html), the SP example every 500 ms [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/example-sitemap.html). Hardening (Field-observed, undocumented): debounce until the route's DOM settles, add a hard ceiling so reinit always runs, ignore reinit requests while one is already scheduled or running, and guard History API / `fetch` patches with a marker property so a re-injected sitemap doesn't wrap them twice. The MutationObserver may restart only the debounce, never the ceiling; otherwise carousels or live prices postpone `reinit()` indefinitely. On re-injection, swap (remove, then add) listeners and intervals instead of skipping them. Automation that navigates with `history.pushState` leaves the previous view mounted, so re-test with real in-app navigation ([field-guide-web.md](field-guide-web.md) §3.4, §4). Add-on code: [sitemap-templates.md](sitemap-templates.md) §4.

### Symptom: Multi-page site records duplicate page views or decisions
- **Cause:** An SPA `reinit()` polling block, often copied from the SP example where it's labelled "SPA Websites" [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/example-sitemap.html), fires when scripts change the URL without navigating (`history.replaceState` for filters, anchors) and re-sends the page interaction (Field-observed, undocumented). `reinit()` is meant for pages whose "content and URL change without a full page reload" [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html).
- **Confirm:** Count `OnInit` events and `/personalization/decisions` requests per full page load; more than one means extra reinit calls.
- **Fix:** Remove the polling block on multi-page sites (starter: [sitemap-templates.md](sitemap-templates.md) §2). For in-page swaps (quick view, variant, filters) send a catalog event such as `QuickViewCatalogObject` with `sendEvent` instead [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-catalog-interaction.html).

### Symptom: Back/forward navigation shows the content twice and records a second impression
- **Cause:** On a back/forward cache (bfcache) restore, the SDK can re-run personalization while the previous render is still in the DOM (Field-observed, undocumented). No bfcache handling is documented.
- **Confirm:** Chrome DevTools → Application → Back/forward cache → **Test back/forward cache**, or navigate away and back. `window.addEventListener('pageshow', (e) => console.log(e.persisted))` prints `true` on a restore; then `document.querySelectorAll('[data-sf-personalization-id]').length` is above 1 and a second `personalization-view` is sent.
- **Fix:** One implementation stopped it with the init option `bfcacheAutoReinit: false` (Field-observed, undocumented; it isn't among the documented `init` fields [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html)). Re-test after every SDK upgrade, and make custom rendering idempotent (remove the previous render before inserting).

## Symptoms: Consent and identity

### Symptom: No events and no personalization on any page, with no console errors
- **Cause:** Consent never reached `Opt In`. The SDK "doesn't store or transmit any collected data until it has been granted explicit consent" and waits for a valid `Opt In` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-consent.html); `consents: []` means no tracking until `updateConsents()` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html). Missing consent behaves as opt-out; implicit opt-in is MCP behavior. Whether `Personalization.fetch` itself is blocked without opt-in is undocumented.
- **Confirm:** `SalesforceInteractions.getConsents()` is empty or shows `Opt Out`, or the purpose isn't `SalesforceInteractions.ConsentPurpose.Tracking` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-consent-data.html).
- **Fix:** Resolve the `consents` Promise from the consent management platform (CMP), or call `SalesforceInteractions.updateConsents({ provider: '<CMP_NAME>', purpose: SalesforceInteractions.ConsentPurpose.Tracking, status: SalesforceInteractions.ConsentStatus.OptIn })` when the visitor grants consent [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-consent.html).

### Symptom: A new device's first page view is missing after the visitor accepts the consent banner
- **Cause:** `init()` can resolve before the `consents` Promise settles, and events sent before opt-in are dropped, not queued, so the initial page interaction is lost (Field-observed, undocumented; consistent with "doesn't store or transmit" [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-consent.html)).
- **Confirm:** In a fresh browser profile, accept consent after the page loads. No page-load interaction (`pageView` `1` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-translating-sdk-events-to-web-connector-schemas.html)) is sent for that page.
- **Fix:** Optional on multi-page sites, where the next full page load is tracked normally. If the first view matters, remember whether the initial page interaction was suppressed, and after the grant call `reinit()` exactly once. Never replay an interaction that already transmitted (Field-observed, undocumented pattern):

```js
let initialViewSuppressed = false;
// inside init().then(), before initSitemap():
initialViewSuppressed = !SalesforceInteractions.getConsents()
  .some(({ consent }) => consent.status === SalesforceInteractions.ConsentStatus.OptIn);
// in the CMP "granted" handler, after the SDK has received Opt In:
if (initialViewSuppressed) { initialViewSuppressed = false; SalesforceInteractions.reinit(); }
```
- **Also (Field-observed, undocumented):**
  - Call `updateConsents()` synchronously at the top of the CMP handler, even when the `consents` Promise settles on the same event.
  - Decide replay only from `getConsents()`: returning visitors can transmit before the CMP publishes.
  - Treat a throwing guard as "already sent", and capture `initialViewSuppressed` immediately before `initSitemap()`.
  - Retry identity binds and profile attributes dropped while the gate was closed.

  Details: [field-guide-web.md](field-guide-web.md) §1.2.
- **Also:** `getConsents()` reports `Opt In`, while Consent Log rows can hold `opt-in` (Field-observed, undocumented; the documented `consentLog` status values are `Opt In` / `Opt Out` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-translating-sdk-events-to-web-connector-schemas.html)). Normalize before comparing: `s.toLowerCase().replace(/[^a-z]/g, '')` yields `optin`.

### Symptom: Signed-in visitors still get anonymous or default decisions
- **Cause:** The `partyIdentification` values don't satisfy the real-time match rule. SP's custom rule matches Party Identification `Identification Number` with `Exact`, limited to the Party Identification Type and Name values you pick [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_setup_real_time_identity_resolution_for_einstein_personalization.htm&release=264.0.0&type=5); the SP mapping sends `IDName` → Identification Name, `IDType` → Party Identification Type, `userId` → Identification Number [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/integrate-salesforce-interactions-sdk.html). Real-time matching allows only `Exact` or `Exact Normalized` (normalized only for email and phone), and a non-exact match returns no profile [src](https://help.salesforce.com/s/articleView?id=data.c360_a_identity_resolution_match_type_compare.htm&release=264.0.0&type=5).
- **Confirm:** Inspect the `partyIdentification` event's `IDName`, `IDType`, and `userId` in `OnEventSend` (`e.detail.actionEvent.user.attributes`), compare them character by character with the match rule, and run Q10a. The SDK translation table calls the field `IDNameWeb` while the SP mapping uses `IDName` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-translating-sdk-events-to-web-connector-schemas.html), so check which one your uploaded schema defines.
- **Fix:** Send exactly the Name and Type strings the rule expects, send the event when the member signs in, and keep `Match on Blank` unchecked [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_setup_real_time_identity_resolution_for_einstein_personalization.htm&release=264.0.0&type=5).
- **Also:**
  - To separate the platform from the browser, call the point on the authenticated endpoint with a source `context.individualId` and `TestMode` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-request-personalization.html). If the decision is right there, the browser session isn't stitched.
  - If web devices with the same identifier also stay separate, check the criterion for a cross-object "Match to" target (Field-observed).
  - After an `IDName`/`IDType` change, older rows fall outside the rule, so filter counts by Name.

  Details: [field-guide-data.md](field-guide-data.md) §1, §3.

### Symptom: Unrelated visitors share one profile, or everyone gets the same "known" decision
- **Cause:** Placeholder identifiers such as `NA`, `anonymous`, or `0` sent as `userId` link every visitor who sends them. Identity resolution docs name placeholder values (for example `000-0000`) as a cause of oversized unified profiles, and a literal `"null"` Identification Number is skipped during matching [src](https://help.salesforce.com/s/articleView?id=data.c360_a_resolution_troubleshooting_ir_errors.htm&release=264.0.0&type=5).
- **Confirm:** Q10b lists the most shared Identification Numbers; Q10c lists the largest unified profiles.
- **Fix:** Send `partyIdentification` only when a real member ID exists, never a placeholder, and clean existing rows at the source or with data transforms [src](https://help.salesforce.com/s/articleView?id=data.c360_a_resolution_troubleshooting_ir_errors.htm&release=264.0.0&type=5).

### Symptom: A second member who signs in on the same device sees the first member's content
- **Cause:** The first-party cookie keeps the same `anonymousId` across sessions [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-identity.html), so the device's Individual stays linked to the first member (Field-observed, undocumented as a merge scenario). Web `partyIdentification` is keyed on `deviceId` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/integrate-salesforce-interactions-sdk.html), so the second member's row overwrites the first and the device's history moves to the second member at the next run (inference from the key); two people aren't fused.
- **Confirm:** `SalesforceInteractions.getAnonymousId()` returns the same value before and after the second sign-in.
- **Fix:** When the signed-in member changes, call `SalesforceInteractions.resetAnonymousId()` (new cookie, "effectively starts a new session") before sending the new member's `partyIdentification`; `clearPersistedIdentities()` clears stored known identities [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-identity.html) [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-integration.html). The methods are documented; the sign-in pattern is field-observed. Detect the switch against a persisted "last bound ID" in `localStorage` (a session value starts empty each session), and never call `setAnonymousId()` to mark a login ([field-guide-web.md](field-guide-web.md) §2.3).

### Symptom: The same visitor becomes a new anonymous profile on each subdomain
- **Cause:** `cookieDomain` defaults to the current site's domain [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-initialization.html), and `setCookieDomain()` after init has no effect until `reinit()` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-identity.html).
- **Confirm:** `SalesforceInteractions.getCookieDomain()` and `getAnonymousId()` differ between subdomains.
- **Fix:** Use `init({ cookieDomain: '<PARENT_DOMAIN>', ... })` on every subdomain [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-identity.html).

## Symptoms: Page types, WPM, and publishing

### Symptom: An experience stopped showing, or reports split, after a sitemap edit
- **Cause:** Page type names are contracts. The sitemap `pageTypes[].name` binds WPM's `Current Page Type` Location (Field-observed, undocumented) and labels events as `sourcePageType` [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-translating-sdk-events-to-web-connector-schemas.html). Renaming one silently detaches experiences and splits reports.
- **Confirm:** `matchStatus` shows the new name as `selected`, and the Q2 page type inventory shows both the old and the new name over time.
- **Fix:** Treat `name` as immutable. If a rename is unavoidable, re-point every affected WPM experience's Location and record the cutover date for reporting.

### Symptom: The wrong page type is selected
- **Cause:** "The very first page type to successfully match the current URL is given the status `selected`", and evaluation stops [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-integration.html). A broad `isMatch` earlier in `pageTypes[]` wins. The `initSitemap` reference instead says multiple page configurations can match and are merged, which is a doc contradiction [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-sitemap.html).
- **Confirm:** Read the `console.table(matchStatus)` output from the triage snippet.
- **Fix:** Order `pageTypes[]` from most to least specific and make `isMatch` functions mutually exclusive.

### Symptom: WPM doesn't list the personalization point
- **Cause:** WPM lists only points built on a real-time profile data graph [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_personalization_point_standard_profile_data_graphs.htm&release=264.0.0&type=5), and only points in the data space configured in the site's sitemap [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_use_predefined_templates.htm&release=264.0.0&type=5). Without `personalization.dataspace`, `fetch` uses `default` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/request-personalization-through-sitemap.html).
- **Confirm:** On the point record, check the profile data graph type and data space; in the sitemap, check `init({ personalization: { dataspace } })`.
- **Fix:** Rebuild the point on a real-time profile data graph in the sitemap's data space, or set `personalization.dataspace`.

### Symptom: The experience template isn't offered in WPM
- **Cause:** The template was stored with **Save**, which keeps it for later, instead of **Save & Activate**, or it isn't connected to this website in the template's "Connect to your site" step [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_experience_template_create.htm&release=264.0.0&type=5). (That inactive or unconnected templates are hidden in WPM is an inference.)
- **Confirm:** Personalization app → **Experience Templates** → open `<TEMPLATE_API_NAME>`: check its activation state, its data space, and its connected websites.
- **Fix:** Connect the website, click **Save & Activate**, then reload WPM.

### Symptom: WPM won't open or the login window never appears
- **Cause:** Third-party cookies are blocked, a popup blocker suppresses the login window, or the user lacks a permission set [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_access_web_personalization_manager.htm&release=264.0.0&type=5) [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_prerequisites.htm&release=264.0.0&type=5).
- **Confirm:** Browser site settings for cookies and popups; the user's permission set assignments. Sandboxes need `sf_personalization_wpm&sf_personalization_wpm_env=prod_sandbox` in the URL [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_access_web_personalization_manager.htm&release=264.0.0&type=5).
- **Fix:** Allow third-party cookies and popups for the site, then click Log In. Assign `Personalization Admin` or `Personalization User` [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_prerequisites.htm&release=264.0.0&type=5); the access page instead names a "Web Personalization Manager user permission set", which is a doc conflict [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_access_web_personalization_manager.htm&release=264.0.0&type=5).

### Symptom: Appending `?sf_personalization_wpm` does nothing or WPM errors on launch
- **Cause:** The string never reaches the page's SDK. Redirects (login, locale, canonical or consent redirects) and client-side routers can drop query parameters, and the page may not have finished loading the Web SDK with the Personalization module (Field-observed, undocumented).
- **Confirm:** On the final page, check the address bar still contains the string. In the DevTools console, `typeof SalesforceInteractions?.Personalization?.launchWpm` must be `"function"`; if it's `"undefined"`, the SDK or its Personalization module isn't on this page ([web-sdk-and-sitemap.md](web-sdk-and-sitemap.md)).
- **Fix:** Launch WPM directly on the loaded page with the documented bookmarklet `javascript:SalesforceInteractions.Personalization.launchWpm()` [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_access_create_bookmarklet.htm&release=264.0.0&type=5). Running `SalesforceInteractions.Personalization.launchWpm()` in the DevTools console does the same (Field-observed, undocumented). Cookie, popup and permission requirements still apply (previous symptom). Chrome bookmarklet steps are in [wpm-experiences-campaigns.md](wpm-experiences-campaigns.md).

### Symptom: The preview looks right, but visitors see nothing or a different decision
- **Cause:** Previewing a specific decision shows it "ignoring any preconfigured targeting rules" [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_preview_the_experience.htm&release=264.0.0&type=5). Nothing publishes until **State** is `Enabled` and you click **Save** again [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_export_and_publish.htm&release=264.0.0&type=5).
- **Confirm:** Preview with **Current User Decision**, which applies targeting to the current user, or enter a different **Individual ID** after the **Preview Settings** tab [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_preview_the_experience.htm&release=264.0.0&type=5) [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_use_predefined_templates.htm&release=264.0.0&type=5). Check the experience's State toggle.
- **Fix:** Set State to `Enabled`, click **Save**, and re-test in a fresh browser profile after granting consent.

### Symptom: WPM save fails with "Please contact support — Unrecognized field "isMapped" at [line:1, column:512]"
- **Cause:** The save API rejected a property in the JSON the WPM client sent. The payload is a single line, so the position points into that JSON, not into your template HTML. This suggests client/server schema skew (Field-observed, undocumented; no doc or known issue found).
- **Confirm:** Reload WPM to see whether the save persisted anyway. In DevTools → Network, capture the failing save request, open the request payload, and find the object that contains `isMapped`.
- **Fix:** Disable browser extensions that patch `fetch`/XHR and retry; retry in a clean browser profile; re-save the point's content schema, then the experience. If it persists, open a Salesforce Support case with the payload excerpt and the response body.

## Symptoms: Decisioning
Diagnostic codes resemble HTTP status codes but aren't; don't read them as such [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html). `EnableDiagnostics` is listed on the Request Personalization page but not in the authenticated endpoint's flag list (`TestMode`, `ContextOnly`) [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-request-personalization.html) [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-authenticated-request.html).

### Symptom: Profile-based targeting rules never match
- **Cause:** The point uses a standard profile data graph. SP skips the profile lookup and "uses a blank, anonymous profile" unless the request carries the profile, so profile-based rules and recommender filters evaluate to false [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_personalization_point_standard_profile_data_graphs.htm&release=264.0.0&type=5).
- **Confirm:** Check the point's profile data graph type. On an authenticated call with `EnableDiagnostics`, look for rule codes `521`/`523` or profile codes `511`–`513` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html).
- **Fix:** Use a real-time profile data graph for web (WPM requires one). For server-side calls on a standard graph, send the profile: the API has a top-level `profile` body parameter ("the API always uses this profile"), while Help says to put it "in the context object" [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-request-personalization.html) [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_personalization_point_standard_profile_data_graphs.htm&release=264.0.0&type=5).

### Symptom: A merge field renders its default text instead of the visitor's value
- **Cause:** No attribute value was found for that visitor, so SP substitutes the configured default text (for example "Dear {first_name}" becomes "Dear Valued Customer") [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_point_decision_add_merge_fields.htm&release=264.0.0&type=5). Typical reasons: an anonymous or unmatched visitor, a standard profile data graph called without the profile, or an attribute that isn't on the point's profile data graph.
- **Confirm:** Preview in WPM with the visitor's **Individual ID**, and check that the attribute exists on the profile data graph; related attributes and calculated insights also need a sort criteria [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_point_decision_add_merge_fields.htm&release=264.0.0&type=5).
- **Fix:** Resolve identity first (see the identity symptoms), add the attribute to the profile data graph, and keep a neutral default text.

### Symptom: The point returns no content for some visitors
- **Cause:** Diagnostic `201 NO_DECISION_QUALIFIED`: the individual qualified for none of the point's decisions [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html). Draft decisions aren't evaluated [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_personalization_point_decision_add.htm&release=264.0.0&type=5).
- **Confirm:** Run an authenticated test call with `EnableDiagnostics`; for browser traffic, the diagnostics are in the Personalization Log [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html).
- **Fix:** Decisions evaluate by priority, which you can reorder [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_personalization_point_decision_add.htm&release=264.0.0&type=5). Order them from most to least specific and end with an `Always (No Rules)` catch-all (inference: the docs describe no default decision).

### Symptom: Diagnostic `401 POINT_NOT_CONFIGURED`
- **Cause:** A typo in the point `name` or `id`, the wrong tenant endpoint, a transient network issue, a failed configuration sync, or conflicting IDs and names across points [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html).
- **Confirm:** Compare the requested name with the point's API name, and `<TENANT_ENDPOINT>` with the connector's endpoint.
- **Fix:** For network issues, retry after 30 seconds; for a sync failure, edit and re-save the point [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html).

### Symptom: Some points in a multi-point request come back empty
- **Cause:** One request must only contain points that "use the same profile data graph" [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-request-personalization.html); the mobile SDK leaves grouping by data graph to the caller [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/personalize-mobile-experiences-android.html).
- **Confirm:** Compare the profile data graph on each requested point.
- **Fix:** Split requests by profile data graph.

### Symptom: Intermittent HTTP 429 from the Decisioning API
- **Cause:** Backend overload (internal diagnostic `406 TOO_MANY_REQUESTS`) surfaces as HTTP `429`, meaning "throttle or hold-off requests" [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html). Recommendation requests are capped at 60,000 per minute per tenant [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_basics_limits.htm&release=264.0.0&type=5).
- **Confirm:** Network status codes, and the number of decision requests per page view (SPA reinit storms multiply them).
- **Fix:** Retry with exponential backoff and jitter, send one request per navigation, and combine points that share a profile data graph into one request.

### Symptom: A point never returns in the browser, or a test with `decisionId` fails with HTTP 400
- **Cause:** A point marked as requiring authentication is evaluated only through the authenticated endpoint [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_personalization_point_considerations.htm&release=264.0.0&type=5). A `decisionId` on an unauthenticated call is diagnostic `408 SPECIFIED_DECISION_NOT_SUPPORTED`, returned as HTTP 400 [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-pipeline-diagnostics.html).
- **Confirm:** Check the point setting and the request path: `/personalization/decisions` vs `/personalization/authenticated/decisions` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-authenticated-request.html).
- **Fix:** Clear the authentication requirement on browser-served points. Do decision-level QA (`decisionId`, `EnableDiagnostics`, and `TestMode`, which records nothing to the data lake) on authenticated calls only [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-request-personalization.html).

### Symptom: Recommendation decisions return an empty `data` array
- **Cause:** A recommender trains only while `Active`; a point can use it only after one successful refresh (`Last Successful Refresh`), and training refreshes every 24 hours [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_recommender_recommender_training_track_status.htm&release=264.0.0&type=5). Objective-based recommenders need at least 3 engagement activities [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_recommender_considerations.htm&release=264.0.0&type=5).
- **Confirm:** On the recommender, read `Latest Refresh Status` (`Processing`, `Complete`, or `Failure`) [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_recommender_recommender_training_track_status.htm&release=264.0.0&type=5).
- **Fix:** Wait for a successful refresh, and attach a fallback recommender that shares the data space, item data graph, and profile data graph [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_recommender_set_up_fallback_Recmdr.htm&release=264.0.0&type=5).

### Symptom: Known visitors' first page isn't personalized, later pages are
- **Cause:** Record caching is off on the real-time data graph: "the first page visited by your known visitors might not show personalization immediately" [src](https://help.salesforce.com/s/articleView?id=data.c360_a_record_caching_in_rt_data_graphs.htm&release=264.0.0&type=5).
- **Confirm:** Check the real-time data graph's record caching setting.
- **Fix:** Enable record caching; entitlements for sub-second real-time profiles and entities aren't consumed while it's disabled, so expect consumption once it's on [src](https://help.salesforce.com/s/articleView?id=data.c360_a_record_caching_in_rt_data_graphs.htm&release=264.0.0&type=5).

## Symptoms: Rendering

### Symptom: "Replace an Element" never renders on an element identified only by an id
- **Cause:** Selector type mismatch. An element with only an `id` must be targeted as `#<TARGET_ID>`; class notation such as `DIV.<TARGET_ID>` matches nothing (Field-observed, undocumented; standard CSS semantics).
- **Confirm:** `document.querySelectorAll('<selector WPM saved>').length` must be 1. The "hiding the following transformations" debug line shows the saved `path` (Field-observed, undocumented).
- **Fix:** Enter `#<TARGET_ID>` in the **Page Element** field, which accepts CSS [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_manually_personalize_page_elements.htm&release=264.0.0&type=5), or re-select with **Select Element** / **Select Parent**. Prefer stable, site-owned ids or `data-*` attributes over generated classes.

### Symptom: Content shows for some users only, and views are missing for that segment
- **Cause:** The target element exists only in some user states (signed in, a tier, a cookie state), or the selector runs through a parent component name that differs between states. The decision still returns, but nothing renders and no view event fires, so reports lose that segment without a visible gap (Field-observed, undocumented).
- **Confirm:** For one user in each state, run `document.querySelectorAll('<TARGET_SELECTOR>').length`, and compare views per segment with page views per segment.
- **Fix:** Ask the site team for a stable, empty, dedicated wrapper present for every user, and target it with `#id` or a `data-*` attribute ([field-guide-web.md](field-guide-web.md) §5).

### Symptom: The content renders twice, or existing content goes blank until the personalized content loads
- **Cause:** Two placement paths for one slot: a sitemap content zone with a selector, plus a WPM `Replace an Element` experience on the same element. Sitemap zones are exposed to WPM as their own targets [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/set-up-content-zones.html). Blank content until load comes from SP flicker defense, which hides the elements that enabled experiences target until render or `redisplayTimeoutMilliseconds`; debug logs list them as transformations with a `path` (Field-observed, undocumented). Hiding content-zone selectors is MCP Flicker Defender behavior; don't assume it in SP.
- **Confirm:** Enable **Show All Personalization Experiences** in Preview Settings [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_use_predefined_templates.htm&release=264.0.0&type=5); count `[data-sf-personalization-id]` elements; look for two hidden paths for one slot in the debug log (Field-observed, undocumented).
- **Fix:** Pick one path per slot: a sitemap content zone with `Replace a Content Zone`, or WPM element targeting with no content zone declared for that element.

### Symptom: Personalized content never shows on slow connections, and the original content reappears
- **Cause:** Flicker defense hides targets for `redisplayTimeoutMilliseconds` (default `2000`), then redisplays them; with `renderPersonalizationAfterTimeoutElapsed` at its default `false`, a late response is not rendered [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/configure-flicker-defense.html).
- **Confirm:** Throttle the network in DevTools and compare the decision request duration with the timeout; Q8 gives server-side latency per point.
- **Fix:** The defaults "are sufficient for most use cases" [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/configure-flicker-defense.html). If needed, raise the timeout or set `renderPersonalizationAfterTimeoutElapsed: true` (content may then appear late), and remove duplicate fetches first.

### Symptom: The rendered content collapses into a narrow vertical strip
- **Cause:** The empty placeholder div sits in a `display:flex; flex-direction:column` parent whose alignment isn't `stretch`, so it measures 0 px wide and the injected content shrinks with it (Field-observed, undocumented; standard flexbox behavior).
- **Confirm:** DevTools → Elements → Computed on the target: width `0px`, and the parent's `align-items` is `center` or `flex-start`.
- **Fix:** In the template CSS (experience templates use HTML and CSS [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_experience_web.htm&release=264.0.0&type=5)), set `width:100%; align-self:stretch` on the target and the template root. Size with container queries rather than viewport media queries, because injected content renders inside page columns. `container-type: inline-size` stops the root from sizing to its content, so it needs the explicit width:

```css
<TARGET_SELECTOR>, .tpl-root { width: 100%; align-self: stretch; }
.tpl-root { container-type: inline-size; }
.tpl-root h2 { font-size: clamp(1rem, 5cqi, 2.25rem); }
@container (max-width: 480px) { .tpl-root .cta { width: 100%; } }
```

### Symptom: A creative inside a creative (duplicated text or buttons)
- **Cause:** The decision's image attribute points to a finished creative, with its own text and button baked in, rendered inside an HTML template that already draws the layout (Field-observed, undocumented).
- **Confirm:** Open the decision's attribute values and load the image URL on its own; compare it with the `<TEMPLATE_API_NAME>` design. If `attributes` arrive as configured, the SDK is working.
- **Fix:** Align assets with the template: art-only images with text in attributes, or full-creative images with an image-only template. Check the decision content before debugging the SDK.

### Symptom: On React, Vue, or Angular pages, content flashes then disappears, or preview cancel doesn't revert
- **Cause:** SDK DOM manipulation conflicts with the framework's virtual DOM; a missing `onRevert` breaks preview cancel, and a bad `path`/`onHighlight` breaks highlighting [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/integrate-personalization-modern-frontend-frameworks.html).
- **Confirm:** The content appears, then vanishes on the next component re-render.
- **Fix:** Register `SalesforceInteractions.Personalization.Config.ContentZoneHandler.set(name, { onReady, onRevert, path })` (never both `path` and `onHighlight`) and pick `Use Content Zone Handler` in WPM, which is offered only when a handler is registered [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/integrate-personalization-modern-frontend-frameworks.html) [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_wpm_use_predefined_templates.htm&release=264.0.0&type=5).

### Symptom: Nothing renders and the console is silent
- **Cause:** SDK logging defaults to `none` (0), so the SDK prints nothing [src](https://developer.salesforce.com/docs/data/salesforce-interactions-sdk/guide/c360a-api-debugging.html).
- **Confirm:** `SalesforceInteractions.getLoggingLevel()` returns `0`.
- **Fix:** Run `SalesforceInteractions.setLoggingLevel('debug')` and walk the triage order. Useful debug lines (Field-observed, undocumented; wording may change): "matched enabled personalization experience config names" (experience matched), "flicker defense currently hiding the following transformations" (targets hidden), "handling personalization response" (render started), "Observing element for visibility" (view tracking armed). Duplicate-render check: `document.querySelectorAll('[data-sf-personalization-id]').length` (attribute Field-observed, undocumented).

## Symptoms: Engagement data and reporting

### Symptom: Views and clicks are sent but never reach Website Engagement
- **Cause:** The event type or its fields are missing from the connector's web schema, or the stream isn't mapped. The docs say "you must update your Data Cloud Web Schema", and a custom destination's `event-type` must be defined in the schema and mapped [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/track-personalization-engagement.html). Schema updates only add, and must retain all previous events and fields. The SP mapping table documents `personalizationId` / `personalizationContentId` mappings only for Product Browse Engagement [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/integrate-salesforce-interactions-sdk.html), so map `userEngagement` fields to Website Engagement's `Personalization Id` / `Personalization Content Id` yourself [src](https://developer.salesforce.com/docs/data/data-cloud-dmo-mapping/guide/c360dm-website-engagement-dmo.html) (inference).
- **Confirm:** Connector → **View Full Schema** includes `userEngagement` with `personalizationId` and `personalizationContentId`; the engagement data stream maps to Website Engagement.
- **Fix:** Add the missing fields with an additive schema update, then fix the data stream mapping.

### Symptom: Manually sent engagement events don't join to the Personalization Log
- **Cause:** Missing or wrong IDs. "Always set `id` and `contentId`": `contentId` is the `personalizationContentId` for a specific product, otherwise the `personalizationId` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/track-personalization-engagement.html). Decisions requested with `TestMode` record nothing to the data lake [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/decisioning-api-request-personalization.html).
- **Confirm:** Q9 counts engagement rows with no matching log row.
- **Fix:** Copy both IDs from the decision response into every manual event, and keep **Turn off auto-engagement tracking** cleared unless you send events yourself [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_experience_template_create.htm&release=264.0.0&type=5).

### Symptom: An engagement signal or query filtered by personalization point returns 0 rows
- **Cause:** The ID was copied from a setup-UI URL (prefix `0Wl`), which isn't the point ID recorded in the Personalization Log (prefix `9pp`) (Field-observed, undocumented; the documented web response example shows a `9pp`-prefixed `personalizationPointId` [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/request-personalization-through-sitemap.html)).
- **Confirm:** Run Q2 for the page type to list the point IDs actually present in the log. For any zero-row query, drop filters one at a time and validate each remaining value with its own `GROUP BY` (page type, action, point) before trusting the result (Field-observed method).
- **Fix:** Use the log's `ssot__PersonalizationPointId__c` value (or the response's `personalizationPointId`) in signal filters and SQL. Website Engagement has no point field, so filter through the related Personalization Log [src](https://developer.salesforce.com/docs/data/data-cloud-dmo-mapping/guide/c360dm-website-engagement-dmo.html).

### Symptom: A signal whose User Identifier is `Individual > Master Profile Id` counts nobody
- **Cause:** `Master Profile Id` wasn't populated on Individuals created by the web connector (Field-observed, undocumented; the SP identity mapping table doesn't map it [src](https://developer.salesforce.com/docs/marketing/einstein-personalization/guide/integrate-salesforce-interactions-sdk.html)).
- **Confirm:** In Data Explorer, open Individual rows created by the web connector; the field is empty.
- **Fix:** Set `User Identifier` to the engagement DMO's own Individual field (for example `Website Engagement > Individual`), as the documented signal examples do [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_es_examples_prod_view_engmt.htm&release=264.0.0&type=5).

### Symptom: An engagement signal isn't offered as a funnel stage, or can't filter on the Personalization Log
- **Cause:** A funnel-stage signal "must have an active relationship with the Personalization Log DMO" [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_analytics_attrib_config_custom_create.htm&release=264.0.0&type=5). A signal made available in flows can't use related objects ("Related object fields are unsupported in flows"), so it can't filter on the log's point field [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_engagement_signals_configure.htm&release=264.0.0&type=5).
- **Confirm:** Data Model tab → Website Engagement → relationships include Personalization Log; on the signal, check whether the flows checkbox was selected.
- **Fix:** Activate the Website Engagement → Personalization Log relationship, and rebuild the signal without the flows option, filtering on the related Personalization Log's point field (one related DMO per signal, N:1 or 1:1 only) [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_engagement_signals_configure.htm&release=264.0.0&type=5).

### Symptom: Attribution numbers don't match event counts or click-through rate (CTR)
- **Cause:** They measure different things. First Touch and Last Touch decide which qualifying engagement gets 100% of the conversion value, not how many events count [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_analytics_attrib_config_custom_create.htm&release=264.0.0&type=5). Funnel stages count individuals, and each stage rate is relative to the previous stage [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_analytics_pers_attrib_intelligence_using.htm&release=264.0.0&type=5), so funnel conversion isn't raw event CTR. The custom-model wizard offered windows `24 Hrs`, `7 Days`, and `30 Days`, with no option under 24 hours (Field-observed, undocumented; the docs show only the predefined `7 days` [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_analytics_attribution_settings.htm&release=264.0.0&type=5)).
- **Confirm:** For the same point and dates, compare Q4's CTR with the Clicks stage conversion on the model's Analytics tab.
- **Fix:** Report event CTR from SQL or calculated insights and conversion from attribution, and label every chart with the model and window. For stages 2–4, **Content Match** links item attribution to the previous stage [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_analytics_attrib_config_custom_create.htm&release=264.0.0&type=5). To stop a click on another point's content being credited, also filter both funnel signals by the same point through the Personalization Log relationship (Field-observed, undocumented practice; signals can filter on one related DMO [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_engagement_signals_configure.htm&release=264.0.0&type=5)). Custom models need `Personalization Intelligence User`.

### Symptom: The Pipeline Intelligence dashboard is empty
- **Cause:** Foundational data installs the `Daily Personalization Uniques` and `Daily Personalization Requests` calculated insights, but they "must be manually scheduled" [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_setup_deploy_foundational_data.htm&release=264.0.0&type=5). The dashboard needs both plus CRM Analytics; installing it needs `Personalization Intelligence User`, and the insights and their queries are billable [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_setup_install_pers_pipeline_dashboard.htm&release=264.0.0&type=5).
- **Confirm:** Calculated Insights tab: check both insights' schedule and last run status.
- **Fix:** Schedule both insights and re-check after their first run.

### Symptom: An experiment shows no results
- **Cause:** Results can take up to 24 hours after the start [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_exp_analytics_status_and_controls.htm&release=264.0.0&type=5), and each cohort needs a sample of at least 1,000 participants [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_exp_considerations.htm&release=264.0.0&type=5).
- **Confirm:** Check the status at the top of the experiment analytics dashboard [src](https://help.salesforce.com/s/articleView?id=mktg.persnl_exp_analytics_status_and_controls.htm&release=264.0.0&type=5) and the per-cohort participant counts (where counts appear is UNVERIFIED).
- **Fix:** Wait at least 24 hours, and size the test so every cohort can reach 1,000 participants.

## Gaps and uncertainties
- All debug-log strings, the `data-sf-personalization-id` attribute, `bfcacheAutoReinit`, and the consent-log `opt-in` casing are field-observed and may change without notice.
- No end-to-end latency is documented for website connector events reaching DMOs.
- Whether `Personalization.fetch` runs before consent is `Opt In` is undocumented.
- Doc conflicts left open: `salesforce:` vs `interactions:` event names; first-match vs merge page-type evaluation; `IDName` vs `IDNameWeb`; WPM permission set naming; `profile` as a top-level body field vs "in the context object"; `EnableDiagnostics` missing from the authenticated flag list.
- Whether WPM hides inactive or unconnected experience templates is inferred, not stated.
